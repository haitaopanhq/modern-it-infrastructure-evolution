## 本章概述

本章从《一图看懂账户与身份安全演进史》的主线展开：现代安全最大的变化，不是防火墙更厚，而是安全边界从“机器可信”“内网可信”迁移到“身份可信”“行为可信”。

真正完整的现代身份安全，是一套从用户身份、工作负载身份、云资源身份、CI/CD 身份，到密钥、策略、审计、供应链的长链路系统。它回答的不是“有没有登录”，而是：谁访问、用什么身份、拿什么凭证、是否可验证、是否可撤销、是否可审计。

过去一周，我们一直在讨论虚拟化、资源池、云平台与云原生架构。它们共同解决的是资源效率问题：如何让计算、存储、网络和应用从具体机器中抽象出来，被统一调度、弹性使用、持续交付。但当应用系统越来越互联，服务越来越开放，甚至 AI Agent 开始拥有接近自主行动能力之后，真正决定数字世界能否继续运转下去的，已经不再只是算力与架构，还有“信任”本身。

早期企业对安全有一种默认认知：安全就是拦住外面的人。服务器放在机房里，账号掌握在运维手里，系统藏在内网和防火墙后面，似乎就足够安全。这个阶段的核心信任对象是机器和位置：只要人在公司、请求来自内网、操作发生在受控服务器上，就被默认为可信。

互联网把这个默认前提真正打穿了。员工开始远程办公，业务开始开放 API，用户开始全球访问，系统也第一次从“内部可信”变成“任何人、任何服务、任何终端都可能接入”。于是过去几十年的安全演进，本质上一直在回答同一个问题：当边界不断消失，企业还能相信谁？

真正变化的从来不是某个安全产品，而是“信任对象”本身。最早企业相信机器，后来相信网络，再后来相信账号、Token 与身份系统。云时代之后，边界继续变得模糊：服务跑在云上，大数据留在本地 IDC，Kubernetes 自动调度，API 被第三方调用，CI/CD 自动部署，AI Agent 开始自主执行任务。安全世界的核心问题也随之改变：过去关注的是“谁能进入系统”，现在必须追问“谁正在代表你行动”。

AI 时代真正危险的地方也在这里。过去账号泄露，最多只是一个人被盗号；如果 Agent 拥有工具调用、数据库访问、工单处理和工作流执行能力，那么被劫持的就不只是账号，而是一个可以持续行动的数字分身。它会替你发请求、调用 API、读取知识库，甚至代表企业触发决策流程。

很多企业今天讨论 AI，仍然把注意力放在模型能力、推理速度和 GPU 成本上。但真正决定 AI 能否进入现实世界的，可能恰恰是身份体系本身。因为当 AI 开始拥有行动能力，安全问题就不再只是数据泄露，而是谁在控制行为。

从 DOS、Unix、Linux 的本地权限，到 AD、LDAP、Kerberos 的企业网络身份；从 Web 安全、防火墙、VPN，到 IAM、OAuth、Zero Trust，再到今天 AI Agent 与模型能力保护，账户与身份安全演进史，本质上就是数字世界“信任边界”不断变化的历史。

## 2.0 账户与身份安全演进史

安全史可以按技术产品切分，但更适合按“企业到底相信什么”来理解。

| 阶段 | 默认信任对象 | 代表技术 | 关键变化 |
|------|--------------|----------|----------|
| 单机时代 | 本地机器和本地管理员 | DOS、Unix、Linux 用户、文件权限、sudo | 安全边界主要在机器内部，Root 与最小权限决定本地控制权 |
| 企业网络时代 | 内网、域和组织目录 | AD、LDAP、Kerberos、域控、VPN | 身份从单机账号扩展到企业网络，登录态开始跨系统流动 |
| Web 与 API 时代 | 会话、Token 和应用身份 | Cookie、Session、OAuth、OIDC、JWT、WAF | 系统暴露到互联网，边界从机房迁移到应用入口和认证协议 |
| 云原生时代 | 工作负载、云资源和短期凭证 | IAM、IRSA、Workload Identity、SPIFFE、mTLS | 服务、Pod、Job、流水线都需要可验证、可轮换、可撤销的身份 |
| 零信任时代 | 每一次访问和每一次行为 | Zero Trust、Policy Engine、持续验证、审计 | 不再默认相信网络位置，而是按身份、设备、上下文和风险持续授权 |
| AI Agent 时代 | 代表人和组织行动的数字执行体 | Agent Identity、Tool Policy、AI Gateway、模型能力保护 | 安全边界从“访问系统”升级为“约束行为”，身份体系成为 AI 进入现实世界的前提 |

这条路径说明，安全并不是在基础设施演进之外另起一套系统。恰恰相反，越是抽象、云化、平台化和智能化，身份就越会成为新的控制面。资源可以被调度，服务可以被编排，模型可以被路由，Agent 可以被自动触发，但所有这些动作都必须回答同一个问题：这个动作是谁发起的，代表谁执行，能做什么，何时过期，失败后能不能审计和回滚。

因此，第 2 章不是把安全放在最后作为合规附录，而是把它接回《IT 基础设施演进之路》的主线：现代基础设施不只是让资源更高效，也必须让信任可表达、可验证、可撤销、可审计。

## 2.0.1 Web 攻击真正改变的不是网站，而是整个安全边界

![Web 攻击真正改变的不是网站而是整个安全边界](https://assets.onwalk.net/%E8%87%AA%E5%AA%92%E4%BD%93/%E8%BA%AB%E4%BB%BD%E4%B8%8E%E5%AE%89%E5%85%A8/2026-05-20/05-%E4%B8%BA%E4%BB%80%E4%B9%88Web%E6%94%BB%E5%87%BB%E6%94%B9%E5%8F%98%E4%BA%86%E6%95%B4%E4%B8%AA%E5%AE%89%E5%85%A8%E4%B8%96%E7%95%8C-%E5%B0%81%E9%9D%A2.png)

过去很多公司都有一种安全幻觉：只要外网防住了，内网就是安全的。

所以很长一段时间里，企业最重视的是防火墙、VPN、DMZ、专线、机房门禁。因为那时大家默认相信一件事：能进入公司网络的人，大概率就是自己人。

这种逻辑在局域网时代确实成立过。员工固定办公，服务器固定在机房，系统边界清晰，业务变化也没那么快。安全更多是在防“有人闯进来”：端口扫描、系统漏洞、病毒木马、服务器入侵。但 Web 出现后，事情彻底变了。Web 最大的改变不是“网页变多了”，而是企业第一次把业务系统直接暴露给陌生人。登录、论坛、支付、电商、后台、API，都开始面对公网用户。

攻击者不再一定要攻破整台服务器。他只需要找到一个输入框、一段脚本、一次请求、一个 Cookie、一条 API，就可能绕过权限、拿到数据，甚至进入后台。SQL 注入、XSS、CSRF、Session 劫持、Cookie 窃取，本质上都在说明一件事：过去系统默认可信的输入，突然变得不可信了。

更麻烦的是，今天的网站背后连接的早已不是简单页面，而是支付、供应链、云平台、企业后台、广告系统、用户资产，甚至 AI 服务。Web 已经从“信息入口”变成了“商业入口”，也就自然变成了最大的攻击面。于是攻击开始产业化。自动化扫描、漏洞交易、钓鱼平台、供应链投毒、AI 生成攻击脚本，让攻击门槛越来越低，而企业系统却越来越复杂。很多公司每天都在上线 API、微服务、SaaS、SDK 和第三方插件，却未必清楚自己到底暴露了多少入口。

这也是为什么传统安全边界越来越失效。过去安全靠“外网危险，内网可信”。但云计算、移动办公、多云、Kubernetes、CI/CD、远程协作，让今天的系统早就没有固定边界。服务随时创建，权限到处流动，身份跨环境访问。所以安全的核心开始从“你来自哪里”，变成“你到底是谁”。IAM、SSO、MFA、OAuth、Zero Trust、Workload Identity，本质上都是在回答同一个问题：当网络位置不再可信，系统该如何重新建立信任？

到了 AI 时代，这个问题还会继续放大。因为访问系统的不再只是人，还有 Agent、脚本、机器人、模型服务和自动化工作流。Web 攻击真正改变的，从来不只是互联网安全，而是整个数字世界的信任结构。

过去安全防的是“有人闯进来”。或许未来安全要判断的是：谁在行动？它能做什么？它为什么被允许这么做？

## 2.1 身份与访问管理 (IAM)

IAM 已经不只是账号系统，而是现代企业的安全控制平面。Keycloak、ZITADEL、Dex、Okta、Auth0 解决的不是单点登录这么简单，而是 SSO、MFA、RBAC、OIDC、SAML、LDAP 联邦，以及跨系统身份治理。

### IAM 核心概念

```
┌─────────────────────────────────────────────────────────┐
│                    IAM 核心模型                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   身份 (Identity) ──→ 认证 (Authentication) ──→ 授权   │
│       │                        │                        │
│       ▼                        ▼                        │
│   用户/服务账户            密码/Token/OAuth             │
│                                                         │
│   授权 (Authorization):                                 │
│   ┌─────────────────────────────────────────────────┐  │
│   │  Subject → Action → Resource → Condition        │  │
│   │   用户    操作      资源      条件              │  │
│   └─────────────────────────────────────────────────┘  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 身份提供商 (IdP)

| 方案 | 类型 | 特点 |
|------|------|------|
| Keycloak | 开源 | 功能丰富，支持 OIDC/SAML |
| Okta | SaaS | 企业级，生态完善 |
| Auth0 | SaaS | 开发者友好 |
| Azure AD | 云服务 | Microsoft 生态 |

### OIDC 认证流程

```
1. 用户 → 应用: 访问资源
2. 应用 → IdP: 重定向登录
3. 用户 → IdP: 输入凭证
4. IdP → 用户: 返回授权码
5. 用户 → 应用: 授权码
6. 应用 → IdP: 换取 Token
7. IdP → 应用: Access Token + ID Token
8. 应用 → 资源服务器: 请求资源 (Bearer Token)
```

## 2.2 RBAC 与最小权限

### RBAC 模型

```
┌─────────────────────────────────────────────────────────┐
│                    RBAC 模型                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   用户 (User) ──┐                                       │
│                 ├──→ 角色 (Role) ──→ 权限 (Permission) │

│                           ▼                             │
│                    ┌──────────────┐                     │

│                    │  (Resource)  │                     │
│                    └──────────────┘                     │
│                                                         │
│  权限模型:                                              │
│  • resource:operation:effect                            │
│  • deployment:create:allow                              │

│                                                         │
└─────────────────────────────────────────────────────────┘
```

### Kubernetes RBAC

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### 最小权限原则

| 原则 | 说明 | 实践 |
|------|------|------|
| 最小权限 | 只授予必要权限 | 按需申请 |
| 权限分离 | 敏感操作多人审批 | 审批工作流 |
| 权限时效 | 临时权限，定期审查 | 临时 Token |
| 权限审计 | 定期审查权限 | 季度审计 |

## 2.3 网络安全与零信任

零信任真正改变的不是某个产品，而是默认逻辑：任何访问都不再天然可信。过去服务之间依赖内网 IP 信任；现在每个 Pod、Service、Job、Agent 都应该拥有可验证、可轮换、可撤销的工作负载身份。SPIFFE、SPIRE、mTLS 和 Service Mesh，都是把机器身份纳入安全边界的方式。

### 零信任架构

```
┌─────────────────────────────────────────────────────────┐
│                   零信任架构                             │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   传统边界模型:                          零信任模型:     │
│   ┌─────────────────┐                 ┌───────────────┐│
│   │   外网          │                 │    任何位置   ││
│   │   ┌───────────┐ │                 │    ┌────────┐ ││
│   │   │  内部网络  │ │                 │    │  验证  │ ││
│   │   │   信任    │ │                 │    │  每次  │ ││
│   │   └───────────┘ │                 │    └────────┘ ││
│   │                 │                 │       │        ││
│   └─────────────────┘                 │       ▼        ││
│                           防火墙    │    ┌────────┐    ││
│                                       │    │  授权  │    ││
│                                       │    └────────┘    ││
│                                       │       │        ││
│                                       │       ▼        ││
│                                       │    资源访问     ││
│                                       └───────────────┘│
│                                                         │
│   核心原则:                                             │
│   • 永不信任，始终验证                                   │
│   • 最小权限访问                                         │
│   • 微分段隔离                                           │
│   • 持续监控                                            │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### Kubernetes 网络策略

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-isolation
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
      - podSelector:
          matchLabels:
            app: frontend
      - podSelector:
          matchLabels:
            app: gateway
  egress:
    - to:
      - podSelector:
          matchLabels:
            app: database
    - to:
      - namespaceSelector: {}
      - podSelector:
          matchLabels:
            k8s-app: kube-dns
```

## 2.4 审计与合规

## 2.6 身份边界取代网络边界

现代安全体系最大的变化，是边界正在迁移。传统企业安全长期围绕网络边界展开：防火墙、VPN、ACL、堡垒机、DMZ 和内外网隔离。那套模型背后的默认假设是“内网天然可信”。但云计算、移动办公、SaaS、多云、Kubernetes、CI/CD 和 AI Agent 出现后，员工不再固定在办公室，服务不再固定在机器上，应用开始跨云漂移，工作负载可能只存在几分钟。网络边界不再足以代表信任边界。

IAM 因此成为现代企业真正的控制平面。Keycloak、ZITADEL、Dex、Okta、Auth0 解决的不是简单登录，而是 SSO、MFA、RBAC、OIDC、SAML、LDAP 联邦和跨系统身份治理。企业真正危险的问题也不再只是“有没有 VPN”，而是：谁能登录，以什么角色登录，登录之后能访问什么资源。很多攻击本质上不是突破防火墙，而是拿到了一个合法身份。

零信任进一步把身份从人扩展到工作负载。现代系统中大量“访问者”并不是员工，而是 Pod、Service、Agent、CI/CD Runner、Terraform、Helm、AI Workflow 和外部 API。SPIFFE、SPIRE、mTLS、Service Mesh 要求 Service A 必须证明自己是 Service A，Service B 也必须被验证。云资源访问也开始从长期 AK/SK 转向短期身份，AWS IRSA、GCP Workload Identity、Azure Workload Identity 和 GitHub Actions OIDC 都在减少永久密钥。

最后，Secret 管理和供应链安全成为部署前门禁。Vault、KMS、External Secrets 解决的是密钥生命周期，而不是换个地方存密码；Cosign、Trivy、SBOM、SLSA、Kyverno 解决的是制品是否可信、来源是否可追溯、部署是否被策略验证。现代安全真正要回答的是：谁访问、以什么身份访问、凭证是否可信、权限是否最小化、身份是否可撤销、行为是否可审计。这才是零信任的底层逻辑。

## 2.7 身份安全演进史：从局域网信任到零信任

这条演进叙事来自公众号"行者深蓝"的历史文章序列，按时间顺序从局域网时代一路走到 AI Agent 时代。每一篇文章标题都是一座里程碑，共同勾勒出数字世界信任边界的重构过程。

### 一图看懂：局域网时代的"内网安全可信"

互联网普及之前，企业网络的默认假设是"内网即安全"：服务器放在固定机房，员工在固定工位通过有线网络连接，拓扑稳定且边界清晰。安全策略极其简单——物理隔离加防火墙加访问控制列表，只要设备接入了公司网络就被默认为可信。这套模型在封闭时代确实管用：攻击面有限，信任关系静态可管理。但它的致命缺陷在于信任与身份彻底脱钩——一个接入内网的攻击者与一个合法员工在网络层面享有几乎相同的信任度。这个默认前提为后续所有的安全困境埋下了伏笔。

### 一图看懂：AD / LDAP / Kerberos 的出现

当企业规模扩大、信息系统增多后，单机账号管理变得不可持续——每个系统有自己的用户表，员工要记十几套密码，管理员需在每台服务器上单独创建账号。AD、LDAP 和 Kerberos 在此痛点下诞生：AD 提供统一身份目录，LDAP 定义目录访问协议，Kerberos 用票据代替密码在网络间传递认证信息。它们的本质贡献不是"统一登录"，而是将身份从单台机器中抽离出来——身份不再属于某台 Unix 服务器的 /etc/passwd，而是属于企业级的目录服务。这是身份第一次成为独立的基础设施层，但它仍然隐含"域内可信"的前提。

### 一图看懂：内网安全为什么越来越容易失控

企业网络快速膨胀，但安全单元并没有同步进化。服务器从几十台变成数百台，Wi-Fi 替代有线端口，BYOD 设备涌入，系统类型越来越杂——Windows 域成员、Linux 堡垒机、遗留 Unix、IoT 设备的安全水位参差不齐。一个被攻破的工作站就能成为横向移动的跳板，一台配置不当的打印机都可能泄漏网络凭证。企业开始痛苦地意识到：不是防火墙不够厚，而是"内网默认信任"的模型本身已经失效。

### 内网可信为什么正在成为历史

当企业把大量业务系统暴露到互联网，内网安全的前提被根本动摇。VPN 看似连接了远程员工和内网，实则把外网边界延伸到了每一台接入设备。更关键的是应用架构从单体走向分布式，工作场景从固定工位走向咖啡厅和家庭办公室——内网不再是安全的，甚至不再是"一个网络"。信任无法建立在物理位置上，身份成为唯一可能的新锚点。

### 一图看懂防火墙与 DMZ 为什么越来越不够用了

防火墙的核心逻辑是"基于端口和协议的访问控制"，它假设能明确定义哪些流量合法。但当应用架构演进到微服务和 API 驱动后，这个假设崩溃了。一个现代系统可能有上百个内部 API，服务之间动态发现、动态路由，端口不再是稳定的隔离维度。DMZ 同样面临挑战：传统 DMZ 将 Web 服务器与数据库物理隔离，但应用层攻击（SSRF、API 滥用、JWT 伪造）根本不依赖网络突破。防火墙能挡住端口扫描，却挡不住一个携带合法 Token 的恶意请求。

### 一图看懂：Web 安全是如何诞生的

Web 让企业第一次把业务系统直接暴露给不可控的用户群体。此前的安全主要关注主机漏洞、网络扫描和病毒防护。Web 出现后，攻击面从操作系统迁移到了应用层。SQL 注入让攻击者直接读取数据库，XSS 让恶意脚本在用户浏览器中执行，CSRF 让受害者在不知情下执行恶意操作。这些攻击的共同特征：它们不攻击防火墙，也不攻击服务器操作系统——它们攻击的是应用程序对输入的信任。Web 安全的诞生，标志着安全主战场从网络层向应用层的永久性转移。

### 一图看懂：Web 攻击为什么越来越危险

Web 攻击不是变多了，而是"工业化"了。早期的攻击是手工的、定向的；今天的攻击是自动化、规模化的——扫描器批量探测漏洞、云基础设施分发钓鱼页面、暗网交易数据库和凭证。更危险的是接入点极度分散：官方站点、移动端 API、开放平台、小程序、第三方集成，任何一个入口失守都可能被自动化工具迅速利用来扩大战果。工业化攻击意味着企业不再能靠"发现漏洞-打补丁"的被动模式应对，防御必须前移到架构层面。

### 一图看懂：Web 安全越来越像一场身份战争

当攻击者不再需要突破网络层，攻击面从端口转移到了登录框、Token 和 API Key，Web 安全的本质就变了——它不再是一道"防火墙是否足够坚固"的问题，而是一场"谁以什么身份做什么"的博弈。Cookie 劫持、Session 固定、OAuth 授权码拦截、JWT 签名绕过，这些攻击的核心目标不是破坏系统，而是窃取或伪造一个合法身份。OWASP Top 10 中失效的访问控制和身份认证缺陷持续占据最高风险位置，正是这一判断的最佳佐证。

### 边界已死，身份当立——Web攻击如何终结了"内网可信"

传统安全模型依赖一个暗含前提：网络位置可以代表信任。Web 时代彻底终结了这个前提。Web 应用的访问者可能是任何人、任何设备、任何地点——来自内网 IP 的请求不代表它来自合法用户，来自外网的请求也不等于攻击。网络位置与身份之间的相关性已经断裂。Web 攻击之所以改变了整个安全世界，不是因为它创造了新漏洞类型，而是因为它摧毁了"内网可信"这条所有传统安全的基石。当这个假设崩塌后，安全的核心问题就变成了一个身份问题：你怎么确定一个请求的发起者有权执行这个操作？

### 一图看懂：Web 攻击真正改变的不是网站而是整个安全边界

Web 攻击的扩散效应远超 Web 本身。当一个企业的支付系统、供应链管理、用户数据平台和 AI 推理都通过 Web API 暴露在网络中时，Web 安全就不再是"网站的安全"，而是整个数字业务的安全。API 网关、限流、认证和审计成为基础设施需求而非应用层的可选配置。Web 攻击催生了安全架构的范式迁移：从网络防火墙为中心的边界防御，转向以身份和 API 为中心的纵深防御。这个认知转变，为 Zero Trust 和云安全模型的诞生铺设了道路。

### 一图看懂为什么云时代开始失去"固定边界"

云计算从根本上改变了"企业网络"的定义。VPC 可以随时创建，Pod 在几秒内启动又销毁，固定 IP、固定端口、固定拓扑在云原生架构中都不再成立。更关键的是，企业的资源不再集中在单一数据中心——多云策略将工作负载分散在不同云平台，SaaS 应用由第三方托管，CI/CD 流水线需要访问多个 API。网络边界从"公司的墙"变成了无数 API 端点。在这种架构中，继续依赖网络位置做信任决策已不可行——位置本身就在流动，信任必须建立在身份而非坐标上。

### 一图看懂：现代身份系统的真实运转逻辑

OAuth 2.0 和 OIDC 解决了云与 API 时代最核心的身份问题：一个服务如何代表用户访问另一个服务。授权码流程确保凭证不经过用户浏览器，Refresh Token 支持长期会话而无需反复输入密码，ID Token 让应用验证用户身份而无需保存密码。OAuth 的真正创新不在加密强度，而在于它建立了一套"令牌代替密码"的委托模型。这个模型的工程含义深远：令牌可以设置有效期、限定作用域、随时撤销。它让身份不再是一个"登录"事件，而是一组可验证、可控制、可吊销的授权声明。

### 一图看懂：为什么 Token 正在变成新的攻击面

Token 解决了凭证泄露问题，但也引入了新攻击面——Token 窃取、重用、泄露，如果被截获就等同于合法身份。更复杂的是 Token 生命周期管理：短 Token 频繁刷新影响体验，长 Token 泄露风险更高。JWT 的无状态特性在带来性能优势的同时，也让 Token 一旦签发就难以撤销。企业在部署 OAuth/OIDC 后往往发现真正的挑战不是实现认证流程，而是 Token 的发放、存储、轮换、吊销和审计体系。Token 就是云时代的"新钥匙"——管理不好钥匙，锁再坚固也无济于事。

### 一图看懂：默认信任为什么正在消失

过去几十年 IT 系统演进的底层动力之一，是"默认信任的范围在持续收窄"。单机时代我们相信本机用户和进程；局域网时代相信内网流量；Web 时代不再相信用户输入，开始做输入验证和参数化查询；云时代不再相信网络位置，开始用 IAM 授权；零信任时代不再相信任何访问请求直到被验证。每一次"默认信任"的退让，都是对一次重大安全事故的反思。默认信任的不断退让不是因为安全产品变多了，而是因为数字世界的攻击面一直在扩张——信任只要出错一次就是系统性灾难。

### 一图看懂：为什么内网不再值得默认信任

横向移动是内网安全退化的核心证据。攻击者不需要正面突破核心系统——只需进入内网任意一个节点，利用默认信任逐步渗透到数据库和域控。SolarWinds 攻击和 Log4j 漏洞都证明了同一事实：内网内部的攻击路径远比外网到内网的路径丰富且难以检测。更关键的是现代企业内网不再只有"自己人"——第三方运维工具、SaaS 代理、云连接器、IoT 网关都在内网中拥有网络路径，任何一个供应链环节的失守都可能演变为持续的内部威胁。内网不再是护城河内的安全区，而是攻击者进入后的狩猎场。

### 一图看懂：机器为什么也需要身份证

传统 IAM 是为人类设计的——有人名、有密码、有登录界面。但现代系统中的"访问者"大部分不再是人类：CI/CD 流水线部署时调用云 API，Kubernetes Pod 通过服务发现通信，Terraform 执行计划时获取资源，AI Agent 推理时调用数据库。这些非人类实体同样需要身份，且需求比人类更苛刻——不能有共享密钥，必须支持自动轮换，需要在毫秒级完成认证。SPIFFE/SPIRE 和 Workload Identity 的出现，正是为了解决机器身份的生命周期问题：把 X.509 证书和 JWT 的管理从人工运维升级为自动化的身份控制面。

### 一图看懂为什么 Zero Trust 怕"先方便一下"

Zero Trust 在理论上高度清晰：永不信任、始终验证、最小权限、持续评估。但在落地中几乎每个企业都会遇到同一个现象——"先方便一下"：先给开发者开个 over-permission 的角色，先允许服务之间不加 mTLS 通信，先留一个没有 MFA 的后门账号。每一个"先方便一下"都在零信任体系上打开一个缺口。更深刻的问题是零信任是一种系统级信任模型，不是某个产品的配置项。它的生效需要身份层、网络层、策略层和审计层的协同——任何一个环节的简化都会让整个体系失效。零信任的本质不是采购产品，而是改造信任基础设施。

### Zero Trust 不是产品，而是一种"默认不放心"的系统

很多厂商将 Zero Trust 包装成下一代防火墙或 VPN 替代品，这误解了零信任的含义。零信任不是安全工具的集合，而是一种架构级的信任模型——其核心是"永远不基于网络位置做信任决策"。这意味着身份必须无处不在：用户身份、设备身份、工作负载身份、API 身份、数据身份。每一次访问请求都必须经过独立的验证和授权评估，无论它来自内网还是外网。零信任的落地需要身份基础设施（IdP、CA、SPIFFE）、策略引擎（OPA、Kyverno）、审计与控制面（SIEM、UEBA）三者协同。它的真正投入不在采购，而在架构改造。

### 统一身份信任体系如何一统"IT江湖"

从 AD/LDAP 到 OAuth/OIDC，再到 Workload Identity 和 Zero Trust，身份系统在三十年间从一个辅助工具成长为 IT 基础设施的控制面。这个趋势的驱动力很简单：当资源可以跨云、跨网络、跨组织流动时，唯一不变的坐标系就是身份。统一身份信任体系的建立不是技术选择，而是架构演进的必然。它的工程含义包括：一个统一的身份目录（IdP），一个通用的授权策略引擎（Policy Engine），一个覆盖人和机器的凭证管理体系，以及一套可审计、可追溯、可吊销的身份操作流程。统一不是大一统，而是让身份成为所有系统共同的信任基座。

### 一图看懂：AI Agent 为什么必须有"身份证"

AI Agent 与传统软件的最大区别不在于"智能"，而在于自主行动能力——Agent 可以接收模糊目标、自主分解为子任务、调用多个工具和 API、根据执行结果调整下一步。这个过程中，Agent 会访问知识库、读取用户数据、调用生产系统 API、甚至触发决策工作流。没有可验证的身份，Agent 的行动就无法被归属、无法被审计、无法被控制。Agent 的"身份证"不是登录密码，而是一组可验证的声明：谁创建的、代表谁执行、被授予哪些权限、权限何时过期。Agent 身份是 AI 系统与现有安全基础设施对接的唯一接口。

### 一图看懂：AI Agent 有权限后，谁来管它？

Agent 拿到权限只是开始，真正的挑战在治理。一个 Agent 可能在数小时内执行数百次工具调用，每次调用的上下文不同，权限需求也不同。静态 RBAC 已经不足以描述 Agent 的授权模型——权限需要根据任务上下文动态计算。Token 的生命周期管理也从"小时级"变为"分钟级"甚至"单次调用级"。Agent 行为的审计与人类也不同：关注的不是"谁登录了"，而是"什么触发了这个工具调用、访问了哪些数据、结果是否符合预期"。Agent 治理是安全体系的下一个结构性挑战——当数字世界中自主行动的执行体越来越多，安全必须从"控制入口"进化到"约束行为"。

## 本章收束

安全体系的演进说明，企业真正要治理的不是单个入口，而是一条身份链路：用户身份、工作负载身份、云资源身份、CI/CD 身份、密钥生命周期、审计日志和供应链来源。谁访问、以什么身份访问、凭证是否短期、权限是否最小、行为是否可审计，才是零信任真正的底层逻辑。

这一章也回扣第 7 章的平台工程：平台一旦成为交付入口，就必须把身份、安全、策略和审计内置到 Golden Path 中，而不是把安全留到上线前人工补票。
