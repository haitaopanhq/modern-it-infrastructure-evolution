## 9.2 Agent 执行任务流程

### 任务执行流程

```
1. 用户输入
   ↓
2. 意图识别 (Intent Recognition)
   - 解析用户请求
   - 提取关键信息
   ↓
3. 任务规划 (Task Planning)
   - 分解为子任务
   - 确定执行顺序
   ↓
4. 工具选择 (Tool Selection)
   - 匹配可用工具
   - 检查权限
   ↓
5. 执行 (Execution)
   - 调用工具
   - 处理结果
   ↓
6. 反馈 (Feedback)
   - 返回结果
   - 确认状态
```

### 示例：部署新服务

```
用户: "帮我部署一个新的 API 服务，名称是 user-api"

Agent 思考:
1. 理解意图：需要部署新服务
2. 检查权限：用户有部署权限
3. 规划步骤：
   a. 创建 Kubernetes Deployment
   b. 创建 Service
   c. 配置 Ingress
   d. 检查部署状态
4. 执行：
   a. 调用 k8s-tool.create-deployment
   b. 调用 k8s-tool.create-service
   c. 调用 k8s-tool.create-ingress
   d. 调用 k8s-tool.wait-for-deployment
5. 返回结果
```

## 9.5 从 ChatOps 到 AgentOps

### ChatOps

- **特点**：通过聊天界面触发操作
- **交互**：人工输入命令，Agent 执行
- **局限**：需要人工持续参与

### AgentOps

- **特点**：Agent 自主决策和执行
- **交互**：人工设定目标，Agent 自动完成
- **优势**：7x24 小时无人值守

### 演进对比

| 维度 | ChatOps | AgentOps |
|------|---------|----------|
| 触发方式 | 手动 | 自动/手动 |
| 执行模式 | 同步 | 异步 |
| 决策 | 人工 | AI + 人工 |
| 监控 | 实时 | 异步 |
| 响应时间 | 秒级 | 分钟级 |

## 9.7 AI Agent 的身份与权限治理

当 Agent 从实验性对话助手进化到具备自主执行能力的运维实体，身份与权限治理就成为其能否进入生产环境的前提条件。本节从身份、权限、审计和治理四个维度展开。

### Agent 为什么需要可验证的身份

传统 API 调用的身份模型是"应用密钥 + IP 白名单"，但 Agent 的工作模式与传统的应用程序有根本不同。Agent 不是被动等待调用，而是主动规划并执行多步骤任务——它可能先调用 K8s API 查询集群状态，再调用 PagerDuty 创建告警屏蔽，然后在 Slack 中通知团队。每一步操作都可能跨越不同的系统和安全域。如果没有一个可验证的身份声明，这些操作的归属就无从谈起。

Agent 的"身份证"需要包含比用户身份更丰富的声明集合：

- **归属声明**：这个 Agent 是由哪个用户或团队创建的，代表哪个组织实体行动
- **能力声明**：Agent 被授权调用哪些工具和 API，每个工具的操作范围是什么
- **时效约束**：身份的有效期，是一次性任务还是持久运行，是否需要在每个执行周期重新认证
- **行为约束**：Agent 是否可以修改数据、创建资源、删除配置，还是在只读模式中执行

这些声明共同构成 Agent 身份的"元数据层"——不是简单地给 Agent 分配一个 API Key，而是让身份本身承载语义化的授权上下文。

工程实践中，Agent 身份可以与 SPIFFE/SPIRE 集成，使用 X.509 SVID 作为运行时身份载体；也可以基于 OAuth 2.0 Client Credentials Grant 为 Agent 签发独立的 Client ID 和 Token。关键不在于采用哪种协议，而在于 Agent 的身份与人类用户的身份在同一套 IAM 体系中管理，避免出现"人的权限归 IdP 管，Agent 的权限靠硬编码"的安全断层。

### Agent 权限的最小化原则

Agent 权限的最小化比传统 RBAC 复杂得多，原因在于 Agent 的"行为空间"是动态的。一个传统应用通常有固定的 API 调用模式，权限可以静态配置；但 Agent 可能今天只做日志查询，明天被要求执行数据库迁移，后天又被用来编排多云部署。

针对 Agent 的权限模型，推荐从以下几个维度实施最小化：

- **工具级权限**：明确 Agent 可以调用哪些平台工具。例如，允许调用 kubectl get/list/watch，但禁止 delete/create/exec。工具级权限是最粗粒度的控制边界。
- **资源级权限**：在工具内部进一步限定范围。Agent 只能查询 default 命名空间的 Pod，不能访问 kube-system 或生产环境的敏感命名空间。
- **操作级权限**：结合请求上下文实施动态策略。Agent 在正常运行时允许只读操作，但在工单审批通过后临时开放写入权限，操作完成后自动回收。
- **数据级权限**：对 Agent 返回的内容做脱敏处理。即使 Agent 有权限查询数据库，应自动屏蔽 passwords、tokens、PII 等高敏感字段。

实现这些动态策略的工具链包括 Open Policy Agent（OPA）和 Kyverno。在 AI Gateway 层面，可以将 Agent 的每个工具调用请求转发到策略引擎做实时评估——评估结果不仅包含"allow/deny"，还包含"审计等级"和"是否需要人工审批"等元信息。

### Agent 行为的审计与追溯

Agent 审计日志与传统审计日志有显著差异。传统日志记录的是"谁做了什么"——用户 alice 在 10:00 创建了一个 Deployment。Agent 审计日志需要记录的是"什么触发了什么"——用户 bob 在 09:55 提交了一个 Jira 工单，Agent 在 10:00 识别到该工单，分解为 3 个子任务，调用了 7 次 API，最终创建了 1 个 Deployment 并更新了 2 个 ConfigMap。

Agent 审计的关键要素包括：

- **调用链追踪**：记录每个工具调用的触发原因、输入参数、执行时间和响应结果。使用 OpenTelemetry 的 trace 机制为 Agent 的每次操作创建完整的调用链。
- **决策日志**：记录 Agent 的每个决策点——为什么选择了这个工具而不是另一个，为什么在执行中途调整了参数，为什么决定跳过某个步骤。这些日志对于事后排查 Agent 的"黑箱行为"至关重要。
- **偏差检测**：定期对比 Agent 的实际执行路径与其规划的预期路径，当出现偏差时生成告警。例如 Agent 计划只读操作但实际触发了写操作，或 Agent 访问了权限之外的命名空间。
- **审计回放**：支持按时间轴回放 Agent 的完整行动序列，包括每个工具调用的前后状态对比。这在 Agent 行为异常或造成事故时是排查问题的关键工具。

### 从 ChatOps 到 AgentOps 的治理演进

ChatOps 时代的治理模型相对简单：人类通过聊天界面触发命令，Agent 作为"指令执行器"存在，每一步操作都有明确的人工指令作为授权依据。进入 AgentOps 时代后，治理模型发生了根本性转变——Agent 不再是"人类指令的忠实执行者"，而是"拥有自主决策能力的执行体"。

治理演进的几个关键变化：

| 演进维度 | ChatOps 治理 | AgentOps 治理 |
|---------|-------------|--------------|
| 授权触发 | 每次操作指令即授权 | 任务级授权，子任务动态派生 |
| 权限粒度 | 角色绑定，静态 RBAC | 上下文感知，动态策略 |
| 审计重点 | 人工指令与执行结果 | 决策链路与调用链追踪 |
| 审批模式 | 人工逐个审批 | 风险分级，规则引擎自动审批 |
| 异常处理 | 人工发现并干预 | 策略引擎实时阻断 + 人工告警 |
| 治理边界 | 单一系统 | 跨系统、跨平台、跨云 |

AgentOps 治理的落地不是推翻 ChatOps 的实践，而是在其基础上叠加一层"自主性控制面"。在 Agent 执行高影响操作（生产环境变更、数据删除、权限提升）时，仍然需要人工审批作为兜底。真正重要的是"默认行为可审计、异常行为可阻断、高风险操作需审批"的三层治理架构——这也是 AI Agent 安全进入生产环境的底线要求。
