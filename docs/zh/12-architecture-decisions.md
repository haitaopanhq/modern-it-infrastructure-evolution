# 第 12 章：系统选型与架构决策

## 本章概述

本章介绍技术选型和架构决策的方法论，涵盖如何做技术选型、成本效益分析、决策树与 ADR、以及典型场景的选型建议。

### 选型维度

| 维度 | 评估内容 | 权重 |
|------|----------|------|
| 功能匹配 | 能否满足业务需求 | 高 |
| 性能 | 吞吐量、延迟 | 高 |
| 成本 | 许可、云资源、人力 | 中 |
| 运维 | 复杂度、可靠性 | 中 |
| 团队 | 学习曲线、人员技能 | 低 |
| 未来 | 扩展性、社区发展 | 中 |

## 12.2 技术权衡分析

### 常见权衡

| 场景 | 权衡 | 建议 |
|------|------|------|
| 开源 vs 商业 | 成本 vs 支持 | 核心业务选商业 |
| 自建 vs 云服务 | 控制 vs 运维 | 差异化自建 |
| 成熟 vs 新技术 | 稳定 vs 创新 | 边缘验证 |
| 集中 vs 分布 | 简单 vs 扩展 | 渐进式演进 |

### 成本构成

```
总成本 (TCO) = 硬件成本 + 软件成本 + 人力成本 + 运维成本 + 培训成本 + 风险成本
```

| 成本类型 | 自建 | 云服务 |
|----------|------|--------|
| 初始成本 | 高 | 低 |
| 持续成本 | 波动 | 稳定 |
| 扩展成本 | 高 | 低 |
| 人员成本 | 高 | 低 |

## 12.3 决策树与 ADR

### 选型决策树示例：数据库

```
需要什么类型的数据库？
    │
    ├─ 需要事务？→ 否 → 向量数据库 / 搜索引擎
    │                    ├─ Milvus (AI 应用)
    │                    └─ Elasticsearch (搜索)
    │
    └─ 需要事务？→ 是 → 数据量 < 1TB？
                      │
                      ├─ 是 → MySQL / PostgreSQL
                      │          ├─ 简单 Web → MySQL
                      │          └─ 复杂查询 → PostgreSQL
                      │
                      └─ 否 → 分布式数据库
                                 ├─ 金融场景 → TiDB
                                 ├─ 全球分布 → CockroachDB
                                 └─ 分析为主 → ClickHouse
```

### ADR (Architecture Decision Record)

```markdown
# ADR-001: 使用 PostgreSQL 作为主数据库

## 状态
已通过

## 背景
需要为新微服务选择主数据库，需要支持：
- ACID 事务
- 复杂查询
- JSON 支持
- 高可用

## 决策
使用 PostgreSQL 15 作为主数据库

## 备选方案
- MySQL 8.0: 社区广泛，但复杂查询较弱
- MongoDB: JSON 友好，但事务支持有限
- TiDB: 分布式，但复杂度高

## 后果
### 正面
- 强大的 JSON 支持
- 丰富的索引类型
- 活跃社区

### 负面
- 需要 DBA 技能
- 复制配置复杂

## 评审日期
2026-05-11
```

## 稳定性工程：从容量规划到成本治理

稳定性不是一个运维指标，而是架构决策、容量策略和成本治理三者共同作用的结果。以下从三个维度梳理这一工程体系的核心逻辑。

### 从单体到分布式：架构演进的主线

服务拆分从来不是技术潮流，而是业务增长的被动选择。单体应用在早期效率最高——一个工程、一套数据库、一台服务器，上线快、维护简单。但当用户量增长到百万级、团队扩张到数十人、发布频率达到每日多次后，单体架构的耦合风险、扩容难点和排障依赖会集中爆发。分布式架构用服务拆分换取扩展性和容错能力，但代价同样明确：链路变长、事务复杂、网络不可靠、排障成本上升。企业做架构决策时不应问

"要不要拆分"，而应问"拆分后的治理成本是否可控"。注册中心（Nacos/ZooKeeper）、配置中心、API 网关、链路追踪和 Service Mesh 等组件不是为了炫耀技术，而是"]]分布式复杂度"的治理代价。业务增长之后，可靠性不再是纯技术问题，而是治理成本问题。

### 容量与成本：规划冗余与闲置的本质

容量规划的核心矛盾是"业务波动"与"资源固定"之间的错配。每个业务在流量曲线上都有明显的峰谷特征：白天高峰、夜间低谷、促销日尖峰、平时闲置。为应对峰值而预留的资源，在大部分时间是闲置的。容量冗余的本质是"]]不确定性买单"：企业不知道峰值到底多高，于是预留安全余量来兜底。

技术团队要回答的不是"要不要冗余"，而是"冗余多少可以接受"。闲置资源不是运维失误，而是架构决策的必然结果——承诺 SLA 就必须预留容量。容量预留的成本核算包括硬件采购、机房空间、电力消耗和运维人力。合理的做法是按业务分级配置弹性策略：核心链路做预留 + 弹性扩缩，非核心链路做按需分配 + 超卖。云计算的优势不是消灭冗余，而是让冗余从自持变共享，从固定成本变可变成本。

### 可靠性与成本：SLA、高可用与故障恢复的财务逻辑

SLA 不是运维口号，而是成本承诺。99.9% 和 99.99% 之间相差一个 9，但成本差距不仅限于额外一倍的冗余机器——还涉及跨可用区部署、数据实时同步、故障自动切换、7x24 值班、灾备演练和审计合规。每增加一个 9，技术复杂度和人力成本都非线性上升。

高可用架构的核心不是平均无故障时间，而是故障恢复时间——MTTR 决定了业务损失。怠速资源、冷备热备、多活架构的投入，最终都要用"避免的业务损失"来核算。用户体验下降带来的流失也是隐性成本：一次慢查询可能损失 5% 转化率，一次宕机可能流失大量用户。

企业需要围绕业务价值做可靠性决策——哪些系统必须高可用，哪些可以接受计划内停机，哪些用 SLA 赔偿替代高投入。成本、性能与体验三者构成不可能三角：每优化一个维度，至少牺牲另一个。稳定性工程就是在这个三角中找到业务可接受的位置。
